## 🟠 Важно

### 1. Supabase Auth: защита от утечённых паролей выключена
- **Где:** настройка проекта Supabase Auth (не код), подтверждено `get_advisors(type=security)`: `auth_leaked_password_protection` — WARN.
- **Проблема:** Supabase может проверять пароль при регистрации/смене пароля через HaveIBeenPwned k-anonymity API — сейчас выключено. Пользователь может поставить пароль из топ-листов утечек.
- **Чем грозит:** credential-stuffing/подбор для аккаунтов с распространёнными паролями — особенно чувствительно для business-аккаунтов (продавец с доступом к приватному ключу магазина через свою сессию... хотя сам ключ и не читается клиентом, скомпрометированный аккаунт продавца всё равно позволяет выписывать чеки от его имени).
- **Фикс:** Supabase Dashboard → Authentication → Policies (Password) → включить "Leaked password protection". Не код, 2 минуты.

### 2. `business_receipts`: владелец магазина может редактировать уже выписанный чек напрямую через REST, в обход `issue-receipt`
- **Где:** RLS-политика `"Enable write access for shop owners"` на `public.business_receipts`, `cmd=ALL`, `qual`/`with_check` = `shop_id IN (SELECT id FROM shops WHERE owner_id = auth.uid())` — без ограничения по колонкам (проверено `pg_policies`).
- **Проблема:** `issue-receipt` — единственное место, где суммы официально пересчитываются и подписываются, но после того как строка создана, ничто не мешает владельцу магазина сделать `PATCH /rest/v1/business_receipts?id=eq.<id>` напрямую (anon/authenticated key) и изменить `net_total`/`vat_amount`/`gross_total`/`status`/`fiscal_hash` на что угодно.
- **Чем грозит:** `receipts.js` и `dashboard-items.js` показывают покупателю данные `business_receipts` напрямую из БД, **не** обращаясь к `verify-receipt` — значит подменённая сумма будет показана покупателю как есть. Реальная защита есть только если покупатель отсканирует QR на `verify.html`: там подпись пересчитывается сервером из текущих значений в БД и не совпадёт с `fiscal_hash` (сама подпись подделать нельзя — приватный ключ недоступен продавцу), так что `verify.html` покажет «недействительна». Т.е. это не подделка фискальной подписи, а **тихая подмена данных в личном кабинете покупателя**, которую заметит только тот, кто явно проверит QR.
- **Фикс:** сузить UPDATE-политику по аналогии с `bind_pending_receipts()` — либо запретить владельцу UPDATE вовсе (чек issued = immutable, для исправлений — новый RPC `void_receipt`/`reissue_receipt` с явной пересчёткой и переподписью), либо ограничить колонки, доступные для прямого UPDATE (например, только `status` для отмены). Минимум — добавить триггер, который запрещает менять `net_total/vat_amount/gross_total/fiscal_hash/receipt_number` после INSERT.

### 3. CDN-скрипты без SRI
- **Где:** `business.html:21-23` (jsPDF, qrcode-generator, Chart.js), `verify.html:22` (jsQR) и `verify.html` (pdf.js, cdnjs) — подтверждено: `grep -c "integrity=" *.html` → 0 по всем страницам.
- **Проблема:** классифицировано как «сознательно пропущено» в бэклоге (B-6) на этапе MVP — согласен с оценкой риска, но для 4 из 5 библиотек (jsPDF 2.5.1, qrcode-generator 1.4.4, Chart.js 4.4.1, jsQR 1.4.0) версии зафиксированы и jsdelivr/cdnjs отдают стабильные файлы — добавить `integrity`+`crossorigin="anonymous"` стоит 10 минут и не потребует пересматривать риск позже. Turnstile (`challenges.cloudflare.com`) — динамический скрипт, SRI туда принципиально не добавить, это ок.
- **Фикс:** сгенерировать SHA-384 хэши для зафиксированных версий (`openssl dgst -sha384 -binary file.js | openssl base64 -A`) и добавить `integrity="sha384-..." crossorigin="anonymous"` к 5 тегам `<script>` в `business.html` и `verify.html`.

## 🟡 Можно отложить

### 4. Смешение валют в аналитике продавца
- **Где:** `js/business-panel.js:1806-1814` — `grossTotals = receipts.map(r => parseFloat(r.gross_total))`, сумма считается по всем чекам магазина и форматируется как `currentShop?.currency` (текущая валюта магазина), без учёта `r.currency` каждого конкретного чека (у каждой строки `business_receipts` своя денормализованная валюта на момент выписки — специально «зафиксирована», см. DB-комментарий к колонке).
- **Проблема:** в текущем UI (`business.html`) поле `#shop-currency` есть только в форме создания магазина (`#create-shop-view`, `business.html:113`), в `#shop-dashboard-view` — интерфейса сменить валюту после создания нет. НО в БД `shops.currency` доступна для `UPDATE` роли `authenticated` без ограничения на уровне колонки (RLS `owners_update_their_shop`, проверено `role_column_grants`) — то есть валюту можно сменить прямым вызовом REST API в обход UI. Если это когда-нибудь случится (или появится настройка в UI) — карточки отдельных чеков (`business-panel.js:101`, использует `r.currency`) продолжат показывать верно, а сводная выручка/статистика начнёт складывать разные валюты как одну.
- **Фикс:** при подсчёте `totalRevenue`/`avgReceipt` фильтровать по `r.currency === currentShop.currency` (и, если нужно, показывать предупреждение/отдельную строку для чеков в другой валюте), либо явно запретить смену `shops.currency` после первого выпущенного чека (constraint/trigger).

### 5. `dashboard-items.js`: нет проверки «дата покупки не в будущем»
- **Где:** `dashboard.html:403,484` (`<input type="date" name="purchase_date" required>`, без `max`), `js/dashboard-items.js` — обработчики добавления/редактирования вещи не валидируют `purchase_date` относительно текущей даты (в отличие от `register.js:141-143`, где для даты рождения такая проверка есть).
- **Чем грозит:** не безопасность, а данные — пользователь может создать вещь с датой покупки в будущем, `warranty_end_date` (generated column) тоже уедет в будущее, прогресс-бар и уведомления отработают технически корректно, но бессмысленно для отображения («истекает через 400 дней» для ещё не купленной вещи).
- **Фикс:** добавить `max="<today>"` в HTML (обновляется динамически) + JS-проверку с тостом, аналогично `register.js`.

### 6. `receipt_items.warranty_months` / `items.warranty_months`: нет верхней границы в БД
- **Где:** `items` и `receipt_items` — CHECK только `warranty_months >= 0`, верхнего предела нет; HTML `max="60"` (`dashboard.html:397,478`) — чисто клиентская подсказка.
- **Чем грозит:** ничего критичного (это собственные данные пользователя), но прямой вызов API может записать неадекватное значение (например, 999999 месяцев), которое сломает отображение прогресс-бара/дней до окончания в edge-кейсах.
- **Фикс:** `CHECK (warranty_months >= 0 AND warranty_months <= 600)` (50 лет с запасом) на обеих таблицах.

### 7. QR-формат по-прежнему не экранирует `|`/`:` в значениях (B-7, из бэклога)
- Подтверждаю оценку бэклога: `verify.js:123-140` (`parseQRData`) использует из распарсенного QR только `SIG` (`parseQRData(...).signature`), остальное приходит от `verify-receipt` и рендерится через `.textContent` (`verify.js:228-263`) — реального риска инъекции нет. Формат остаётся хрупким по факту (название товара с `|` в чужом генераторе QR сломает парсинг), но это не в текущем скоупе Valuon. Не блокер.

### 8. `bind_pending_receipts()` — SECURITY DEFINER, исполняем `authenticated` напрямую по REST
- **Где:** `get_advisors` подсвечивает это как WARN; функция (см. `pg_proc`) сама берёт email из `auth.jwt()->>'email'` (не из параметра клиента) и трогает только `status: pending → verified` для чеков с этим email — **проверено, поведение безопасно**, это ожидаемый и документированный паттерн (соответствует `ARCHITECTURE.md` §5.1). Линтер не знает про это — можно оставить как есть, WARN ложноположительный.
