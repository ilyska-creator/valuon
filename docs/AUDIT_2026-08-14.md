## 🟠 Важно

### 1. `business_receipts`: владелец магазина всё ещё может переписать выписанный чек напрямую через REST — вчерашняя находка НЕ исправлена, несмотря на коммит с похожим описанием
- **Где:** RLS-политика `"Enable write access for shop owners"` на `public.business_receipts`, `cmd=ALL`, без ограничения по колонкам — подтверждено свежим запросом к `pg_policies` сегодня. Отдельно подтверждено через `information_schema.role_column_grants`: роли `anon` и `authenticated` имеют `UPDATE`-грант на **все** колонки таблицы, включая `net_total`, `vat_amount`, `gross_total`, `fiscal_hash`, `status`, `receipt_number`.
- **Что произошло:** коммит `2da46ed` (13 авг, «Close email enumeration + receipt tampering...») закрыл **другую** дыру — широкую UPDATE-политику для **покупателя** (заменена на RPC `bind_pending_receipts()`, которая теперь трогает только `status`). Проблема владельца магазина, описанная в `docs/AUDIT_2026-08-13.md` как «Важно #2», в этом коммите не упоминается и в БД не изменилась: политика `"Enable write access for shop owners"` идентична вчерашней.
- **Эксплойт:** авторизованный владелец магазина, зная `id` своего же чека (виден в дашборде продавца), может отправить
  ```
  PATCH /rest/v1/business_receipts?id=eq.<id>
  Authorization: Bearer <его собственный JWT>
  { "gross_total": 1.00, "net_total": 1.00, "vat_amount": 0 }
  ```
  через obычный fetch/curl с anon-ключом (тем же, что лежит в `js/supabase-client.js`) — Postgres примет запрос, RLS пропустит (это его же магазин). `receipts.js`/`dashboard-items.js` у покупателя читают `business_receipts` напрямую из БД и покажут заниженную сумму как есть. Реальный `fiscal_hash` при этом рассинхронизируется с суммами — чек **провалит** проверку на `verify.html` (сервер пересчитывает подпись из текущих значений), но это заметит только тот, кто явно отсканирует QR.
- **Чем грозит:** тихая подмена данных, которые видит покупатель (например, продавец задним числом занижает сумму в случае спора/возврата, или меняет `payment_method`/`purchase_date`). Не позволяет подделать саму подпись (приватный ключ недоступен), но подрывает доверие к тому, что покупатель видит в личном кабинете без сканирования QR.
- **Фикс:** сузить политику `"Enable write access for shop owners"` — либо разбить `cmd=ALL` на отдельные `INSERT`/`DELETE` (без `UPDATE` вовсе — чек `issued` иммутабелен, для отмены/исправления сделать `void_receipt()`/`reissue_receipt()` RPC с явным пересчётом и переподписью), либо оставить `UPDATE`, но отозвать табличный грант и выдать `GRANT UPDATE (status) ON business_receipts TO authenticated` — точечно только на `status` (для будущего сценария отмены продавцом). Дополнительно — триггер `BEFORE UPDATE`, который бросает исключение при попытке изменить `net_total/vat_amount/gross_total/fiscal_hash/receipt_number/customer_email` после INSERT, как защита на случай, если кто-то забудет про грант в будущей миграции.

### 4. Смешение валют в аналитике продавца
- **Где:** `js/business-panel.js:1831-1843` — `grossTotals = receipts.map(r => parseFloat(r.gross_total))` суммируется без фильтра по `r.currency`, подписывается как `currentShop.currency`.
- **Подтверждено сегодня:** `shops.currency` по-прежнему `UPDATE`-грантована `authenticated` без ограничений (проверено `role_column_grants`), UI для смены валюты магазина после создания всё ещё нет — риск теоретический, но не закрыт архитектурно.
- **Фикс:** прежний — фильтровать по `r.currency === currentShop.currency` при подсчёте статистики, либо запретить смену `shops.currency` после первого чека.

### 5. Нет проверки «дата покупки не в будущем» в `dashboard-items.js`

- **Фикс:** прежний — `max="<today>"` + JS-проверка с тостом, как в `register.js`.

### 6. `items.warranty_months` / `receipt_items.warranty_months` — нет верхней границы в БД
- **Где:** проверено сегодня напрямую в БД: `items_warranty_months_check` = `CHECK (warranty_months >= 0)`, `receipt_items_warranty_months_check` = `CHECK (warranty_months >= 0)` — верхнего предела как не было, так и нет.
- **Фикс:** прежний — `CHECK (warranty_months >= 0 AND warranty_months <= 600)`.

### 7. QR-формат не экранирует `|`/`:` — риска на практике нет (без изменений)
- Подтверждено: `verify.js` использует из QR только `SIG`, остальное — от `verify-receipt` через `textContent`.

## Новое с 13 августа — проверено и подтверждено хорошим

### Server-side rate-limiting на `verify-receipt` (не было явно проверено во вчерашнем аудите)
- **Где:** `supabase/functions/verify-receipt/index.ts` — новая таблица `public.verify_attempts` (RLS enabled, без публичных политик — только `service_role` изнутри функции) + RPC `check_and_log_verify_attempt(p_ip_hash, p_fiscal_hash, p_limit=20, p_window='1 minute')`.
- IP берётся из **последнего** элемента `X-Forwarded-For` (не первого) — корректно, так как первый элемент подделываем клиентом, последний дописывает ближайший доверенный прокси перед функцией. Это закрывает потенциальный брутфорс `fiscal_hash` через `verify.html` (перебор случайных подписей на угад), который не был явно в фокусе ни одного из предыдущих аудитов. Хорошая находка авторов, отмечаю как подтверждённую и корректно реализованную.

### Новые UI-пути (searchable категории, custom-select) — проверены на XSS, чисто
- `js/devices.js` (новый файл, статический список `DEVICE_TYPES`) → `renderDeviceTypeOptions()` строит `<option data-icon="...">` только из фиксированного статического массива, не из пользовательского ввода; `deviceIconMarkup()` возвращает HTML по алиасу `map[type] || map.other` — инъекция невозможна, даже если `receipt_items.category` (свободный текст без CHECK-ограничения на значения) содержит произвольную строку: она используется только как ключ поиска в `DEVICE_ICONS`, не рендерится как HTML напрямую нигде (`js/dashboard-items.js:346`).
- `js/custom-select.js` — `icon.innerHTML = iconHTML` (строки 133, 215) получает `iconHTML` из `data-icon`, который в свою очередь всегда идёт из `deviceIconMarkup()` — тот же вывод.
- `js/business-panel.js` (`renderReceiptCards`, автокомплит email) — `escapeHtml()` применяется последовательно ко всем полям из БД (`item_name`, `customer_email`, `status`, `receipt_number`, `payment_method`, `pos_serial`), включая места, добавленные/тронутые последними коммитами.
