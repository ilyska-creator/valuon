## 1. Вёрстка — общие проверки (на КАЖДОЙ странице)

### Шапка / навигация
- [ ] Логотип не съезжает, не размывается при масштабе
- [ ] Меню на десктопе — все пункты в одну строку, не переносятся криво
- [ ] Бургер-меню на мобильном открывается/закрывается, не блокирует скролл фона намертво (закрывается свайпом/тапом вне меню)
- [ ] `sidebar-overlay` в дашборде реально появляется под сайдбаром на мобильном (проверить визуально на реальном телефоне, не только в devtools — CSS-класс `.active` есть, но поведение на реальном тапе нужно перепроверить)
- [ ] Активный пункт меню подсвечен корректно на каждой странице
- [ ] Тоггл темы (☀️/🌙) переключает мгновенно, без "мигания" белым/чёрным (FOUC) — инлайн-скрипт в `<head>` должен успевать до отрисовки
- [ ] Тоггл языка меняет текст без сдвига layout (EN-текст короче/длиннее RU не ломает кнопки/карточки)
- [ ] Хедер не перекрывает контент при скролле (sticky/fixed позиционирование)
- [ ] Cookie-баннер (`cookie-banner.js`) — показывается один раз, «Принять» сохраняет согласие в `localStorage['cookie-consent']`, не появляется повторно при перезагрузке

### Общая типографика и отступы
- [ ] Ни один текст не обрезан/не наезжает на соседний элемент ни в одной локали
- [ ] Длинные email/названия магазинов/имена/названия товаров не переполняют карточки (`overflow`/`text-overflow: ellipsis` или перенос)
- [ ] Все интерактивные элементы (кнопки, ссылки, чекбоксы) — не менее 44×44px на мобильном (тап-таргет)
- [ ] Между блоками нет "прыгающих" отступов при смене темы
- [ ] Placeholder-тексты в полях видны и не сливаются с фоном ни в одной теме
- [ ] Иконки (Font Awesome) прогружаются и не показывают "квадратик"/пустое место при медленном интернете

### Формы (все страницы с формами)
- [ ] Фокус на поле — виден чёткий outline (для клавиатурной навигации)
- [ ] Состояние ошибки поля — видно визуально (цвет рамки + текст ошибки + иконка, не только цветом — для дальтоников)
- [ ] Состояние успеха — видно явно
- [ ] Кнопка submit — показывает спиннер/disabled-состояние во время запроса (защита от двойного сабмита)
- [ ] Автозаполнение браузера/менеджера паролей не ломает стили полей (жёлтый фон Chrome autofill); поля `customer-email` в бизнес-панели используют трюк `readonly` → снятие на focus — проверить, что автозаполнение туда всё равно не лезет
- [ ] На мобильном — правильный `inputmode`/`type` (email-клавиатура для email, `inputmode="numeric"` для сумм/количества)
- [ ] Zoom при фокусе на input на iOS не срабатывает нежелательно (шрифт полей ≥16px)
- [ ] `custom-select.js` (кастомный селект): открывается кликом и Enter/Space, закрывается Escape/Tab/кликом вне, стрелки вверх/вниз перебирают опции, поиск по вводу текста (`data-searchable`) фильтрует список
- [ ] `custom-datepicker.js`: открывается кликом на поле и по клавиатуре, стрелки перемещают фокус по дням (шаг 7 = неделя), Enter выбирает дату, Escape закрывает, «Сегодня»/«Очистить» работают, для `datetime-local` — отдельный пикер времени тоже работает с клавиатуры

### Toast / модалки / оверлеи
- [ ] Toast-уведомления не перекрывают критичные кнопки/поля
- [ ] Toast исчезает сам по таймеру и по крестику
- [ ] Несколько toast подряд — стекуются аккуратно, не накладываются
- [ ] Модальные окна: скролл фона блокируется (`modal-open` класс на `<html>`), пока модалка открыта, и снимается при закрытии в любом сценарии (включая быстрое переключение между несколькими модалками подряд)
- [ ] Модалка закрывается по клику вне, по Esc, по крестику — все 3 способа работают (`modal-a11y.js` — focus trap: Tab не уводит фокус за пределы модалки, после закрытия фокус возвращается на элемент, который её открыл)
- [ ] Модалка на мобильном не выходит за границы экрана, скроллится сама, если контента много
- [ ] Модалка выписки чека в `business.html` — если есть несохранённые изменения, попытка закрыть показывает guard-подтверждение («сохранить черновик / выйти без сохранения»), а не закрывает молча

### `index.html` (лендинг)

- [ ] Badge "Альфа доступ" — не наезжает на заголовок на маленьких экранах
- [ ] Карточки фич — одинаковой высоты в ряд на десктопе, красиво стекуются на мобильном

- [ ] Футер — все ссылки кликабельны, не обрезаны, ведут на все 12 страниц проекта
- [ ] Если пользователь уже залогинен — `checkAuthOnHome()` подменяет CTA на "В личный кабинет", а не показывает "Начать бесплатно"

### `login.html` / `register.html` / `reset-password.html`
- [ ] Форма отцентрована на всех разрешениях, не "прилипает" к краю на широких мониторах
- [ ] Turnstile-капча (Cloudflare) — рендерится корректно, не съезжает, адаптивна на мобильном
- [ ] Ссылка "Забыли пароль" / "Нет аккаунта? Зарегистрироваться" — видна, не теряется
- [ ] Индикатор силы пароля (`password-strength.js`) — 5 требований (8+ символов, заглавная, строчная, цифра, спецсимвол) подсвечиваются по мере набора, а не только после сабмита
- [ ] Поле подтверждения пароля — сообщение о несовпадении появляется по blur/input, не только после сабмита
- [ ] Выбор валюты по умолчанию (`register.html`, `#currency`) и даты рождения (`custom-datepicker`) — работают, дата рождения не даёт выбрать будущую дату

### `dashboard.html`
- [ ] Три вьюхи (`#view-items`, `#view-notifications`, `#view-settings`) переключаются без перезагрузки страницы, активный пункт сайдбара/bottom-nav совпадает с открытой вьюхой
- [ ] Внутри «Моих вещей» — 2 вкладки: «Мои» (ручное добавление) и «Подтверждённые» (из чеков продавцов); состояние вкладки сохраняется в `sessionStorage['valuon-items-tab']` между визитами в рамках вкладки браузера
- [ ] Карточки статистики (активные/истекающие/истекшие гарантии) — не съезжают на планшетной ширине, число анимируется при первой отрисовке
- [ ] Уведомления (колокольчик) — счётчик непрочитанных корректный
- [ ] Пустое состояние (у нового пользователя без единой вещи) — выглядит завершённым, с явным CTA «Добавить вещь», а не как баг
- [ ] Настройки профиля — все поля сохраняются, форма не сбрасывается при ошибке валидации одного поля; смена валюты по умолчанию влияет только на новые записи, не пересчитывает старые

### `receipts.html`
- [ ] Две вкладки: «Личные» (загруженные покупателем) и «От партнёров» (business-чеки); переключение с анимацией fade, без дублирования контента
- [ ] Личные: сетка адаптивная (N колонок десктоп → 1 колонка мобильный)
- [ ] Загрузка файла (drag&drop зона) — работает через drag&drop и через клик; на мобильном открывает камеру/галерею; принимает jpg/png/gif/webp/pdf, отклоняет остальное с понятным сообщением; лимит 10 МБ проверяется до отправки
- [ ] Превью загружаемого файла (фото/PDF, первая страница через `pdf.js`) отображается перед сохранением
- [ ] Личный чек можно привязать к конкретной вещи (select) — при выборе поля суммы/даты/магазина подставляются из вещи и блокируются (`readOnly`, иконка замка), датапикер тоже блокируется через `_cdp.setLocked`
- [ ] Business-чеки — только просмотр/скачивание PDF, редактирование и удаление недоступны (это чек от продавца, а не собственная запись)
- [ ] Business-чек с несколькими товарными позициями — все позиции видны в карточке, каждая со своим сроком гарантии
- [ ] Просмотр личного чека (`btn-view-receipt`) открывает файл в новой вкладке по подписанному URL (TTL 1 час — если карточка «протухла» после часа простоя, URL должен успеть перевыпуститься при показе)
- [ ] Удаление личного чека — запрашивает подтверждение, реально удаляется и запись из БД, и файл из Storage
- [ ] Скачивание business-чека повторно генерирует тот же PDF (логотип, QR, товары) без похода за новой подписью

### `business.html` (бизнес-панель)
**До регистрации магазина:**
- [ ] Форма регистрации: название, налоговый номер, адрес, страна (`custom-select`, searchable), валюта — все обязательные поля отмечены, ошибки видны
- [ ] Логотип (drag-drop, PNG/JPG ≤2 МБ) — необязателен, при превышении размера/неверном формате понятная ошибка
- [ ] После сабмита — пара ключей Ed25519 генерируется на сервере (Edge Function `create-shop`), UI показывает "Магазин создан с криптографической подписью" без демонстрации самого ключа (ключ не должен ни разу появиться в консоли браузера/Network — приватный ключ не должен передаваться клиенту ни в одном ответе)

**Кассы (POS-терминалы):**
- [ ] Добавление кассы (название, серийный номер, модель, локация) — серийный номер уникален в рамках магазина, попытка дублировать даёт понятную ошибку
- [ ] Список касс — активные/деактивированные визуально различимы
- [ ] Деактивация кассы — уже выписанные с неё чеки не теряют пометку кассы, но касса пропадает из выбора при новой выписке
- [ ] Удаление кассы, у которой есть история чеков — предусмотренное поведение (блок удаления или мягкое скрытие) не приводит к ошибке в консоли

**Выписка чека:**
- [ ] Email покупателя — валидируется по формату; список автокомплита из истории покупателей текущего магазина открывается при вводе, клик по варианту подставляет email
- [ ] Динамическое добавление/удаление позиций — работает без визуальных багов при 1, 5, 20+ позициях
- [ ] На каждой позиции: название, количество, цена, ставка НДС, гарантия (мес.), скидка (%, 0–100), категория (свободный текст) — валидация каждого поля (кол-во > 0, цена ≥ 0, гарантия ≥ 0)
- [ ] Итоговая сумма (нетто/НДС/брутто) пересчитывается сразу при изменении любого поля любой позиции, без лагов, скидка применяется корректно к строке до расчёта НДС
- [ ] Выбор кассы (опционально) и способа оплаты (карта/наличные) — сохраняются
- [ ] Черновик чека автосохраняется в `sessionStorage` при незапланированном закрытии вкладки/обновлении страницы — при повторном открытии формы предлагается восстановить
- [ ] Отправка — суммы и подпись считаются на сервере (Edge Function `issue-receipt`); экран успеха показывает номер чека, статус (привязан к клиенту / ожидает регистрации), итоговую сумму, кнопки «Скачать PDF» / «Новый чек» / «Готово»
- [ ] PDF-чек — логотип рядом с названием продавца (не в шапке), QR-код читаемый, номер кассы виден, суммы корректны, товары со скидкой показывают верную сумму по строке
- [ ] Печать/скачивание PDF на мобильном — не блокируется popup-блокировщиком браузера

**Аналитика:**
- [ ] Переключатель периода (неделя/месяц/год) — перерисовывает оба графика (количество чеков, выручка) без дублирования canvas
- [ ] Пустое состояние графика (нет чеков за период) — понятное сообщение, а не пустой холст
- [ ] Графики перекрашиваются при смене темы (light/dark) без перезагрузки страницы
- [ ] Наведение на точку графика — крестообразный курсор (`crosshairPlugin`) и тултип с точными цифрами

**Список выданных чеков:**
- [ ] Статус (выдан/ожидает регистрации) — читаемый бейдж, соответствует полю `status` в БД
- [ ] Список подгружается/пагинируется корректно при большом количестве чеков

### `verify.html` (публичная проверка подлинности, доступна БЕЗ логина)
- [ ] Сканер QR через камеру — запрашивает разрешение камеры корректно; при отказе — понятная ошибка + предложение загрузить файл вместо камеры

- [ ] Копирование результата в буфer (кнопка "Скопировать") — копирует все поля, включая номер кассы, если он есть
- [ ] Кнопка "Назад" — если пришёл параметр `?from=`, ведёт на исходную страницу ТОЛЬКО если это один из разрешённых путей (`/dashboard.html`, `/business.html`, `/receipts.html`, `/index.html`) того же origin; попытка подставить внешний домен в `from=` не должна никуда вести (это уже защищено allowlist'ом в коде — стоит перепроверить при любых изменениях `verify.js`)

### `about.html` / `privacy.html` / `terms.html` / `roadmap.html`
- [ ] Длинный текст читаем, есть межстрочный интервал, не "простыня"

## 3. Функционал — полное покрытие по флоу

### Регистрация / вход / восстановление пароля
- [ ] Регистрация с валидным email — успешна
- [ ] Регистрация с уже существующим email — понятная ошибка, а не generic "что-то пошло не так"
- [ ] Регистрация с некорректным email (без @, без домена) — блокируется на клиенте до отправки
- [ ] Пароль слабее 8 символов / без цифры / без спецсимвола / без заглавной — блокируется, индикатор требований показывает, чего не хватает
- [ ] Возраст: дата рождения младше 16 лет или "старше" 120 — блокируется с понятным сообщением
- [ ] Чекбокс согласия с условиями использования — обязателен, без него форма не отправляется
- [ ] Вход с верными данными — успешен, редиректит в дашборд
- [ ] Вход с неверным паролем — понятная ошибка, без утечки "email существует/не существует"
- [ ] Клиентский rate-limit при множественных неудачных попытках входа (10/15 мин) — срабатывает с понятным сообщением на текущем языке интерфейса (не захардкожено на русском — сообщение формируется в `auth.js` с учётом `lang`); помнить, что это UX-подсказка, а не единственная защита — реальный барьер это Turnstile-капча + серверные лимиты Supabase Auth, которые тоже стоит попробовать обойти прямым запросом к Auth API в рамках пентеста, а не полагаться только на то, что клиентский счётчик сработал
- [ ] Восстановление пароля — письмо приходит, ссылка рабочая, с истечением
- [ ] Смена пароля через reset-ссылку — работает, старый пароль после этого не подходит
- [ ] Logout — реально завершает сессию (после logout нельзя вернуться назад кнопкой браузера и увидеть приватные данные)
- [ ] Истечение сессии (токен протух) — корректный редирект на login, а не белый экран/ошибка в консоли
- [ ] Captcha (Turnstile) — блокирует сабмит без прохождения

### Личный кабинет — «Мои вещи» (покупатель, ручное добавление)
- [ ] Добавление вещи — все 24 типа устройств из `devices.js` доступны в селекте, с иконкой и переводом на RU/EN
- [ ] Обязательные поля (название, дата покупки) не дают сохранить пустую форму; необязательные (бренд, серийный номер, место хранения, цена) можно оставить пустыми
- [ ] Гарантия = 0 месяцев — карточка показывает «Без гарантии» (пунктирный трек), товар исключён из статистики и уведомлений
- [ ] Гарантия — отрицательное число в поле (например, вставить `-5` вручную или через devtools) — теперь блокируется на уровне БД (`CHECK warranty_months >= 0`) и клиент дополнительно не даёт уйти в минус; это регрессионный тест после фикса 13 августа 2026 — обязательно перепроверить при любых изменениях формы добавления/редактирования вещи
- [ ] Гарантия — граничные даты: покупка 31 января + 1 месяц, покупка в будущем, покупка ровно сегодня — расчёт дней до конца гарантии не даёт неожиданных отрицательных/огромных чисел
- [ ] Статус гарантии (активна/истекает ≤30 дней/истекла/без гарантии) — совпадает между карточкой в "Мои вещи" и текстом уведомления для одной и той же вещи (общая логика `calculateDaysLeft`, но функция задублирована в двух файлах — при правке одного проверить и второй)
- [ ] Редактирование вещи — сохранённые изменения применяются, отменённые (Cancel) — не применяются, поля подтягиваются из текущей записи корректно
- [ ] Удаление вещи — запрашивает подтверждение, реально удаляется
- [ ] Кнопка «Добавить в календарь» на карточке (только у вещей с активной гарантией) — скачивает `.ics`-файл (`calendar-export.js`) с правильной датой окончания гарантии, названием вещи и магазином, открывается в Google/Apple/Outlook календаре без ошибок парсинга
- [ ] Валюта вещи — при отображении цены используется валюта, сохранённая при создании записи, а не всегда валюта по умолчанию из профиля

### «Подтверждённые товары» (из чеков продавцов-партнёров)
- [ ] Товары из business-чеков на email пользователя появляются автоматически, без ручного действия
- [ ] Карточка verified-товара — read-only (без кнопок редактировать/удалить), явно отличается визуально от карточки «моей» вещи
- [ ] Множественные позиции одного чека — каждая превращается в отдельную карточку товара со своим сроком гарантии
- [ ] Чек, выписанный ДО регистрации покупателя (`status: pending`) — после регистрации на тот же email автоматически привязывается и появляется в «Подтверждённых» (проверить именно через реальную регистрацию нового аккаунта на email, на который заранее выписан чек)

### Уведомления
- [ ] Уведомление о скором истечении гарантии (≤30 дней) — появляется, текст со склонением дней корректен на обоих языках
- [ ] Уведомление об истёкшей гарантии — появляется с числом дней "просрочки"
- [ ] Товары без гарантии (0 месяцев) — не создают уведомлений
- [ ] Отключение уведомлений в настройках (`expiry_alerts`) — список уведомлений сразу показывает состояние «уведомления отключены», а не пустой список молча
- [ ] Уведомления не дублируются при повторном рендере/обновлении страницы

### Бизнес-панель — сквозные проверки (см. также раздел 2 про вёрстку конкретных блоков)
- [ ] Регистрация магазина — работает один раз; при повторном заходе с существующим магазином сразу показывается дашборд магазина, а не форма регистрации заново
- [ ] Выдача чека с ОДНОЙ позицией — подпись создаётся, чек появляется у покупателя
- [ ] Выдача чека с НЕСКОЛЬКИМИ позициями — сумма считается верно на сервере (браузер отправляет только цену/кол-во/скидку/НДС по позициям, финальные суммы и подпись возвращает `issue-receipt`, а не собственный расчёт браузера — если в интерфейсе сумма разошлась бы с тем, что реально записалось, это баг сервера, а не рисовки)
- [ ] Отрицательная/нулевая цена товара — блокируется валидацией и на клиенте, и (если обойти клиент через прямой запрос к Edge Function) на сервере
- [ ] Выбор способа оплаты — сохраняется, отображается покупателю на понятном языке независимо от текущей локали интерфейса покупателя
- [ ] Проверка email покупателя — при вводе email продавец видит подсказку об истории (из автокомплита прошлых покупателей своего магазина), но НЕ получает прямого ответа "зарегистрирован ли этот email в Valuon вообще" — это сознательно закрыто на уровне сервера (было дырой до фикса 13 августа 2026: RPC `check_profile_exists` был публично вызываем и позволял перебирать чужие email; теперь вызывается только сервером внутри `issue-receipt`) — при любых будущих изменениях формы выписки чека проверить, что эта проверка не возвращается на клиент напрямую

### Верификация чека (публичная, без логина) — функционал
- [ ] Сканирование валидного QR — показывает "Подлинный", данные чека, включая товары
- [ ] Сканирование QR несуществующего чека — "Не найден"
- [ ] Сканирование QR с испорченной/чужой подписью — "Подпись недействительна", а не "Не найден" (два разных состояния)
- [ ] Больше 20 проверок подряд с одного IP за минуту — включается серверный rate-limit, ответ понятен пользователю
- [ ] Повторное сканирование того же валидного чека — не создаёт побочных эффектов в БД, кроме записи в лог попыток

### Настройки профиля
- [ ] Смена email — требует подтверждения на новый адрес
- [ ] Смена пароля из настроек (не через reset) — требует ввода текущего пароля
- [ ] Удаление аккаунта (если реализовано в текущей версии UI) — предупреждает о необратимости; если не реализовано — явно не должно быть полурабочей кнопки, которая ничего не делает
- [ ] Смена языка интерфейса — сохраняется между сессиями (`localStorage['valuon-lang']`)
- [ ] Смена темы — сохраняется между сессиями, синхронизируется между вкладками одного браузера (`themeChange` событие)
- [ ] Смена валюты по умолчанию — влияет только на новые вещи/чеки, не пересчитывает задним числом уже существующие записи

### Общие сквозные сценарии
- [ ] Полный E2E: регистрация продавца → создание магазина → добавление кассы → выдача чека на email существующего покупателя → чек сразу появляется у покупателя со статусом «подтверждён» → покупатель сканирует QR на `verify.html` → верификация проходит
- [ ] Полный E2E: выдача чека на email НЕЗАРЕГИСТРИРОВАННОГО покупателя (статус «ожидает») → регистрация нового аккаунта на этот email → чек автоматически появляется как подтверждённый
- [ ] Работа без интернета / при потере соединения на середине действия (отправка формы) — понятная ошибка, а не зависание
- [ ] Работа на медленном 3G (throttling в devtools) — все спиннеры/скелетоны показываются, ничего не выглядит "сломанным" из-за задержки
- [ ] Открытие ссылки на `verify.html` с валидным QR-параметром в новой вкладке / шеринг ссылки — работает без авторизации
- [ ] Одновременное открытие бизнес-панели в 2 вкладках одного магазина — черновик чека и список касс не конфликтуют разрушительно (последний сохранённый черновик может перезаписать другой — не критично, но не должно приводить к ошибке в консоли)

## 4. Переводы (RU ↔ EN) — построчная проверка

Метод: переключить язык на КАЖДОЙ странице и визуально пройти сверху вниз, ища:
- нетронутый текст (остался на другом языке или показан ключ `data-i18n="..."` вместо перевода);
- обрезанный/наехавший текст из-за разной длины RU/EN;
- некорректный грамматический род/число ("у вас 1 чеков" вместо "1 чек");
- неправильный/смешанный формат даты и чисел между локалями (разделитель тысяч, десятичный разделитель).

Файлы для сверки (проверить оба языка на каждый): `script.js` (лендинг), `login-lang.js`, `dashboard-lang.js`, `business-lang.js`, `verify-lang.js`, `about-lang.js`, `privacy-lang.js`, `terms-lang.js`, `roadmap-lang.js`, плюс встроенные RU/EN-строки в `devices.js` (24 типа устройств), `password-strength.js` (5 требований к паролю), `calendar-export.js` (текст .ics-события), `security.js` (сообщения rate-limit — теперь локализуются на стороне вызывающего кода в `auth.js`/`register.js`, а не внутри `security.js`).

## 8. Безопасность — регрессионные проверки

Пункты ниже подтверждены на 13 августа 2026 через прямую проверку кода и живого состояния Supabase (RLS-политики, гранты на колонки, тела Edge Functions). При любом изменении соответствующего кода — перепроверять заново, а не доверять галочке из прошлого прогона.

### Подтверждено исправлено (перепроверять при изменениях смежного кода)
- [ ] Валюта — нигде не осталось захардкоженного `$`, используется `formatCurrency()` с полем `currency` записи
- [ ] `String(id).slice(...)` — везде обёрнуто в `String()` перед `.slice()` (в `business-panel.js`, `receipts.js`, `receipt-generator.js`)
- [ ] Пароль при регистрации — реально требует 8+ символов, заглавную, строчную, цифру, спецсимвол (не только `length < 6`)
- [ ] Сообщение rate-limit при входе — localизуется по текущему языку интерфейса, не захардкожено на русском
- [ ] `verify.js`, параметр `?from=` — ведёт только на allowlist путей того же origin; подстановка внешнего домена не работает
- [ ] `check_profile_exists` (RPC) — НЕ вызывается напрямую с клиента ни на одной странице; прямой запрос к `/rest/v1/rpc/check_profile_exists` с anon-ключом должен возвращать ошибку доступа, а не результат
- [ ] `business_receipts` — у покупателя нет прямого UPDATE на таблицу; привязка `pending → verified` идёт только через RPC `bind_pending_receipts()`, которая не даёт менять ничего, кроме статуса своих же чеков
- [ ] `shops.public_key`/`private_key` — не передаются клиенту в ответах `create-shop`/`issue-receipt` (кроме `public_key`, который открыт намеренно); прямой INSERT в `shops` с указанием `public_key`/`private_key` через REST должен быть отклонён правами доступа
- [ ] `items.warranty_months` — отрицательное значение отклоняется и на клиенте, и на уровне БД

### Известные, сознательно принятые риски (не блокер, но держать в голове)
- [ ] SRI/integrity для CDN-скриптов всё ещё не добавлены — принятый риск на этапе MVP
- [ ] QR-формат не экранирует строго `|`/`:` в значениях — не эксплуатируется в текущей архитектуре (верификация серверная, `textContent` при рендере), но при любом изменении `verify.js` в сторону доверия содержимому QR-строки без сервера — переоценить риск заново
- [ ] Клиентский rate-limit логина/регистрации — в памяти вкладки, сбрасывается перезагрузкой; реальная защита — Turnstile + серверные лимиты Supabase Auth
- [ ] Leaked Password Protection в Supabase Auth — по состоянию на 13 августа 2026 всё ещё выключена (сознательно отложено)
